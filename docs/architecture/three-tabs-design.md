# Design: three tabs and reverse engineering

Approved by the PO on 2026-11-17 (D-007 amended, D-019 to D-021). Implemented incrementally:

| PR | Scope | Status |
|---|---|---|
| A | Three tabs, shared real data in memory and `sessionStorage`, leg aliases. No change in calculation behaviour. | Merged (#7) |
| B | Scenario engine for reverse engineering (pure domain + tests): `src/domain/scenarios/`. | Merged (#8) |
| C | Tab 3 UI: three scenarios, per-leg allocation, manual own-CT control. | This PR |

## 1. One app, three tabs (D-019)

A single page that shows one of three tabs. The active tab is reflected in the URL hash
(`#commission`, `#next-level`, `#target`):

- the browser's back/forward buttons move between tabs instead of leaving the app;
- a reload keeps the tab;
- no server configuration is needed (the hash never reaches the server), whatever the hosting.

| Tab | Content |
|---|---|
| **Mi comisión actual** (`#commission`) | The real data (market, CT, points per generation, legs with alias and VE) and the estimated commission. No hypothetical simulations. «Borrar mis datos». |
| **Mi siguiente meta** (`#next-level`) | Current level and amount, what is missing for the next level (own CT route) and the step chart. |
| **Ingeniería inversa** (`#target`) | Target amount → points needed. Today the own-CT route; PRs B and C add the team scenarios. |

The simulation tabs always work: without real data they start from zero (planning ahead), with a
non-blocking notice and a link to tab 1 (PO, 2026-11-17).

## 2. Code layout

```
src/
  domain/commission/   engine (unchanged)
  domain/scenarios/    reverse-engineering scenarios (PR B)
  state/               real data model, sessionStorage, shared context (single source of truth)
  app/                 App shell, tabs model, hash hook, tab navigation
  components/          shared form components (NumberField, MarketFields, GenerationFields, LegFields)
  shared/              formatting
  features/current/    tab 1
  features/next-level/ tab 2
  features/target/     tab 3
```

Two separate models:

- **Real data** (`PartnerData`): edited only in tab 1, read by every tab through
  `usePartnerData()`.
- **Scenario** (PR B): `{ ownExtra, legExtras: { [legId]: points } }`, local to tab 3, never
  written back. A pure `applyScenario(real, scenario)` builds the hypothetical engine input.

## 3. Persistence (D-007 as amended)

Nothing leaves the browser. Within the open tab, the real data is kept in `sessionStorage`
(key `tcg-commission-calculator/partner-data/v1`, shape-checked on load): it survives reloads
and back/forward navigation and is deleted when the tab closes or with «Borrar mis datos»
(nothing is kept when the form is empty). Scenarios are never stored. Storing data across
sessions would need a server and a database (not decided).

## 4. Legs (D-020)

Each leg is `{ id, alias, volume }`: a stable ID, an optional first name chosen by the partner
(default «Pata N»), and the VE from the Online Office. Aliases never reach the engine. Points
per generation are entered as before; coherence warnings (Σ legs ≤ downline, missing legs) stay.

## 5. Reverse-engineering scenarios (D-021, PR B and C)

**Key property.** The estimated commission never decreases when points are added, whether own
CT or points to any leg: adding to a leg never lowers TT or TT-n, so the level never drops.
Hence a binary search along any allocation direction finds the exact minimum *in that
direction* (verified by property tests).

**Team assumption.** Extra points of a leg are generated by its direct partner (generation 1):
they raise generation 1, the leg's VE, TT, and possibly TT-1/2/3; the leg order is recomputed
in every evaluation (a weak leg may become the strongest).

**Allocation strategies** (each defines a direction; binary search finds the scale):

| Strategy | Idea | Use |
|---|---|---|
| Levelling (water-filling) | Raise the weakest legs up to the next one, never overtaking the strongest | Usually the fewest points to reach a level (TT-n grows 1:1) |
| Proportional | Proportional to each leg's current VE | «Each one grows at her pace» |
| Equal | Same points per leg | Easiest to explain |

**Candidates.** Strategies × own-effort shares (0, 10, 25, 40, 50, 60, 75, 90 % of the own-only
minimum); each binary search lands on level jumps by itself, so target levels need no separate
loop. About 750 engine calls, ~20 ms per target. Keep the non-dominated
candidates (no other needs both less own CT and fewer team points), then pick:

1. **Solo yo**: own-only minimum. *Exact minimum.*
2. **Mi equipo y yo**: the most balanced non-dominated candidate (minimises
   max(own / own-only minimum, team / team-only minimum)). *Proposal (heuristic).*
3. **Mayor aportación del equipo**: the candidate with the least own CT. *Proposal.* If not
   reachable (e.g. below level 1, no legs), say so and why.

Duplicates (equal to two decimals) are removed. Every displayed scenario is re-evaluated
with the engine; if rounding of the per-leg split leaves it short of the target, it is bumped
up. **Manual control:** fix the extra own CT; find the minimum team points for each strategy and
show the best.

**Display** per scenario: extra own CT, team points in total and per leg (by alias), final CT,
VE, VE-1/2/3, level, estimated commission and difference to the target, worded as conditions
(BR-21), with the generation-1 assumption and the new-partner rule (BR-23) explained.

## 6. Regressions watched in PR A

Market preselection, coherence warnings, the 7 locales, the strongest-team note (now with the
leg's alias), the step chart and all existing tests. Checked in Chromium (mobile): deep link to
a tab, data shared between tabs, back/forward, reload, «Borrar mis datos» and no external requests.

## 7. Tab redesign (PO, 2026-11-17)

Testing showed that mixing points per generation and legs in one tab confused two different
things: **generations give the commission, legs give the level**. Each tab now has one purpose
and its own data:

| Tab | Purpose | Inputs | Output |
|---|---|---|---|
| **Mi comisión actual** (`#commission`) | The reality, as in the Online Office (imported when available, D-018; typed otherwise) | CT, points per generation, the partner's own VE-1, VE-2, VE-3 (her row in the Office list) | Level and commission. No legs. |
| **Planificar mi meta** (`#plan`) | Play with the points, like the team planner sheet | Target level first; then «Yo» and each leg: forecast for the month and, optionally, made so far | Requirement-by-requirement comparison with the target, own CT needed with the legs as planned, level reached with a motivational message, % above its main requirement, points missing per day until month end, estimated commission (approximate) and the step chart |
| **Ingeniería inversa** (`#target`) | «I want to earn X» | Target, own CT she is willing to make, her legs (each with what she expects, or a count and an average) | Whether the plan is enough; if not: more own CT (exact), more from the legs with own CT as planned, a combination, and how many more partners at the average |

- TT-n is built by adding the legs that are not the strongest (BR-06), so it is never negative.
- **Approximate commission of a plan:** legs only give team totals, so their points are spread
  over generations like the real generations of tab 1 (or all in generation 1 without data).
- Tab 3 is independent and usable from empty; it is prefilled from the plan of tab 2 (also when
  the plan is only kept on the device, D-023). Buttons reload the plan's legs at any time: real
  partners only, or all including fictitious ones (D-024).
- Each tab keeps its form in `sessionStorage` (D-007). The plan of tab 2 can also be kept in
  `localStorage` with an opt-in checkbox until the goal is reached (D-023, Q-22 option B).
- Tab 2 starts with the month planned (month and year, D-025); «made so far» and the pace only
  apply to the current month.
- A leg can be marked as a fictitious (planned) partner: the plan then reminds that she must
  join the month before the goal month and suggests 10 business conversations per partner (D-024).
- Legs can be reordered with ↑ ↓ buttons in tabs 2 and 3 (order is display only; the engine
  sorts legs by VE). Yearly history and fortnightly follow-up of
  the planner sheet wait for a server and a database.
- Motivational messages per reached level come from the planner sheet (editable texts).
